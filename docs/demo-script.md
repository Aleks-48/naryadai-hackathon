# Демосценарий НарядAI

Демо работает на синтетических данных. Никакие действия не отправляются наружу.

## 3 минуты · основной сквозной цикл

1. Войдите как `master01 / demo123`. На доске видна демо-команда и актуальная очередь; покажите индикатор локального обновления.
2. Нажмите «Выдать наряд». Выберите шаблон «Насос · вибрация», исполнителя `worker01` по логину в подсказке выбора (статус/загрузка видны), срок 6–8 часов и приложите уникальное фото «до» до отправки формы. Для синтетического демо можно выбрать `demo_photos/synthetic-sample-a.jpg`; API сохраняет фото и наряд атомарно. Образец — не фото оборудования.
3. Выйдите и войдите как worker01 / demo123. Новый выданный наряд уже содержит проверенное уникальное фото «до». Пройдите «Поставить в очередь → Принять из очереди → Начать исполнение → Приостановить → Продолжить»; для паузы укажите причину. Фото «до» в этом сценарии приложено для демонстрации; по ТЗ его отсутствие не блокирует выдачу или принятие.
4. Заполните отчёт о работе, при желании добавьте отдельный комментарий исполнителя, выберите код неисправности и часы; отметьте, что материал не использовался. Не загружайте фото и зафиксируйте «Исполнено».
5. Проверка запускается автоматически после фиксации «Исполнено». При стандартной конфигурации интерфейс прямо показывает `rules-only`; внеплановый наряд без фото переходит в «Доработка».
6. Начните доработку, загрузите небольшое фото «после», повторите отчёт и проверку. Проверьте карточку/аудит; затем войдите как мастер, явно выберите оценку 1–5, укажите комментарий-обоснование и финально закройте наряд. Покажите эту оценку и причину в сессии исполнителя.

Сценарий подчёркивает, что фото не доказывает исправность; допускает опасную работу только уполномоченное лицо предприятия.

## До 7 минут · дополнительные функции

- Выдайте второй наряд всей бригаде; посмотрите кандидата с наименьшей загрузкой и что один исполнитель закрепляется после принятия.
- Отклоните наряд с причиной, переназначьте его мастером и посмотрите обе записи в журнале.
- Откройте доску и фильтры по участку, оборудованию, исполнителю, приоритету; покажите отдельный флаг просрочки.
- Сравните число активных задач и очередь исполнителя, посмотрите историю оборудования.
- Откройте отчёт за произвольный диапазон, отфильтруйте бригаду/смену. Покажите часы, материалы, выдано/исполнено/закрыто, просрочки и паузы из аудита; уточните, что смена отчёта определяется временем события в учебном UTC-расписании, текущая загрузка показана отдельно, а пауза не является подтверждённым простоем.
- В карточке покажите выставленную при закрытии оценку мастера и основание, затем при необходимости скорректируйте её с новой причиной и покажите аудит. Общий рейтинг за период и оценка одного наряда — разные показатели. При наличии подходящей истории вручную свяжите повтор с предыдущим закрытым нарядом, укажите основание, покажите автора связи и возможность отзыва. Автоматического штрафа без этой связи нет.
- Войдите как `manager / demo123`: экран аналитики доступен только для чтения.

## Резервная ветка

Если на показе нет внешней модели или интернета, продолжайте в `rules-only` и не называйте его LLM. Если требуется настоящий push, это отдельная согласуемая интеграция: этот локальный проект хранит события в очереди, но не отправляет их на телефон.

## Telegram · локальная fake-проверка

Локальные тесты отправляют приватные update JSON в тестовый HTTP-сервер и перехватывают вызов Bot API fake sender. Они проверяют постраничный список для исполнителя/мастера/руководителя, пустой список, чужие назначения, повтор update ID, старую очередь после смены назначения/роли и лимиты входа. Токенов нет; запуск живого бота и отправка сообщений не выполняются.

История из 540 записей: 1 июля 2026 05:00 UTC — 1 октября 2026 13:54 UTC (более 90 суток). Ещё 10 записей LIVE показывают все десять статусов.

## Manual queue ordering

1. Sign in as master01 / demo123 and create two planned orders for worker15.
2. In the queue panel, select the second order in its worker queue and use the up arrow. Confirm its position changes while priority and status remain the same.
3. Sign in as worker15 / demo123 and confirm the new position is read-only and shared. A manager also has no reorder control.
4. Open two master sessions, save from one, then submit from the stale session. It must receive HTTP 409 and refresh before retrying.
5. Reassign an active order and verify that the old queue revision changes; a stale reorder is rejected.

The Telegram list is read-only and reflects saved positions. No Bot API token or external message is part of this demo.
