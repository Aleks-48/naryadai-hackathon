# НарядКонтроль

Локальный MVP для Qostanai AI Industry Hackathon 2026, кейс №1. Стек: Python 3.12, SQLite, HTTP API, адаптивная PWA и Pillow для безопасного декодирования изображений, EXIF и поиска похожих файлов.

## Запуск

Откройте PowerShell в папке проекта и выполните:

```powershell
.\start.ps1
```

Для локального запуска API без UI установите Python-зависимость Pillow: `python -m pip install -r requirements-api.txt`. Для Streamlit AppTest и веб-интерфейса используйте закреплённые версии из `requirements-streamlit.txt`; корневой `requirements.txt` предназначен для Streamlit Community Cloud.

Если политика PowerShell блокирует скрипт:

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
```

Либо запустите напрямую:

```powershell
& 'C:\Users\777\Documents\Codex\2026-09-30\task-2\.venv\Scripts\python.exe' .\server.py
```

Откройте `http://127.0.0.1:8765`. Первый запуск автоматически создаёт SQLite, каталог фотографий и 550 синтетических нарядов. По умолчанию они находятся в `data/`; переменная `NARYADAI_DATA_DIR` задаёт постоянный каталог. Остановка — `Ctrl+C`.

## Зарегистрированный простой оборудования

В панели отчётов мастер может вручную внести закрытый интервал UTC и причину регистрации. Запись идемпотентна по ключу запроса и попадает в отдельный audit-event; мастер видит собственные интервалы, руководитель — общий список только для чтения. Отчёт обрезает интервалы по UTC-периоду и при выборе смены — по UTC-окнам A/B/C, затем объединяет перекрытия отдельно для каждой единицы оборудования. Фильтр бригады к этому журналу не применяется. Паузы исполнителя по `pause/resume` и фактические `labor_hours` остаются самостоятельными показателями.

Это ручная регистрация, а не телеметрия и не подтверждение исправности или состояния машины; никаких простоев система не выводит автоматически. Интервал и причина не влияют на рейтинг работника. Маршруты описаны в [API](docs/api.md), поведение — в [матрице требований](docs/requirements-and-scope.md).

Краткий сценарий на 3 минуты и расширение до 7 минут — в [docs/demo-script.md](docs/demo-script.md). Проект помечает синтетические данные в интерфейсе. Фото «до» необязательно при выдаче обоих типов наряда. Мастер может добавить до 5 фото из камеры или галереи в карточке наряда в статусе «выдан» или «очередь». Без фото «после» отчёт внепланой работы получит «доработку» при проверке; мастер не сможет закрыть наряд без исправления. Фото и время загрузки не доказывают свежесть съёмки, исправность оборудования или допуск к опасной работе.

Исправления P0 включают выбор исполнителя/бригады для переназначения отказанного наряда, рабочие обработчики кнопок связи повтора, отдельный комментарий при закрытии, ввод количества расходников в Streamlit, Telegram-шаблоны просрочки с ограниченными данными и устойчивую отметку отправки с повторной проверкой прав перед отправкой. Исторические DEMO-записи без неизменяемого подтверждения происхождения автоматически не исправляются.

## Режимы ИИ и интеграции

- Проверка текста завершения наряда через Gemini/OpenAI-compatible Chat Completions опциональна. По умолчанию внешний LLM выключен; его можно включить только вручную через `NARYADAI_LLM_ENABLED=1`, `NARYADAI_LLM_API_KEY` и `NARYADAI_LLM_MODEL`; `NARYADAI_LLM_API_URL` необязателен, пустое значение использует Gemini endpoint, любой заданный адрес должен быть HTTPS. Без включенного и полного конфига сервер остаётся в явно помеченном `rules-only`; timeout — 12 секунд.
- При текстовой LLM-проверке отправляется JSON с отчётом и ограниченным контекстом: исходная проблема (до 1200 символов), оборудование (160), код неисправности (120), тип работ, до 20 строк материалов (SKU 80, наименование 160, единица 24 символа, количество), отметка о неиспользованных материалах, трудозатраты, время относительно дедлайна и число уникальных фото после работы; отчёт обрезается до 8000 символов. Обрезание отмечается; при недостатке ключевых данных или обрезании автоприёмка блокируется и нужна проверка мастера. Дедлайн — цель по сроку заявки, а не утверждённая трудовая норма. LLM не разрешает опасные работы и не заменяет финальное решение мастера.
- Детектор удаляет часть очевидных контактов и значений с метками `password`/`token`/`API key`, но не обещает универсальную анонимизацию произвольного текста. Внешнюю LLM используйте только с синтетическими демо-записями; не отправляйте реальные производственные или личные данные. Fake-тесты проверяют передачу полей и защитные правила, но не оценивают точность реальной модели.
- Дополнительная LLM-сводка смены выключена отдельно. Для неё требуются `NARYADAI_LLM_REPORT_SUMMARY=1` и явный запрос из экрана отчёта. Она доступна мастеру/руководителю только при пяти и более нарядах и отправляет только даты и агрегированные счётчики/часы, не текст нарядов, имена, единицы оборудования или коды неисправностей. В среде с секретами LLM это внешняя передача данных; запускайте только на одобренной конфигурации.
- Фотоконтроль принимает JPEG/PNG/WebP до 4 МБ и не более пяти активных фото каждой фазы. Точный или похожий дубль отклоняется с отдельным audit-событием без сохранения файла, фото-строки, имени или содержимого запроса. При возврате на доработку предыдущие фото «после» становятся неактивными, запись загрузки и событие замены остаются в аудите, а media-файлы очищаются после commit; восстановленную старую запись API не отдаёт. Если очистка временно не удалась, новая загрузка ждёт её завершения.
- EXIF извлекается из DateTimeOriginal или DateTimeDigitized с offset соответствующего поля. Без даты время съёмки неизвестно; без записанного часового пояса сервер не подставляет часовой пояс. Уникальное активное фото оценивается по проверяемости файла (3 — без даты EXIF, 4 — с датой, 5 — с датой и часовым поясом). Низкий балл или дата за пределами окна требует явного решения мастера. Окно по умолчанию 60 минут, настройка `NARYADAI_PHOTO_CAPTURE_WINDOW_MINUTES`; это проверка согласованности, не доказательство свежести. EXIF можно изменить, фото не подтверждает свежесть или исправность.
- Похожесть вычисляется 64-битным dHash через Pillow с ограничением цветового профиля; порог — расстояние Хэмминга ≤6 и близкая средняя цветовая подпись. Это сигнал повторного использования, не доказательство; сильное кадрирование/поворот может обойти сравнение. PWA перед отправкой уменьшает фото до 1600 px и сжимает в JPEG; EXIF переносится при поддержке браузера. Сервер хранит перекодированную версию. Даже EXIF и время загрузки не доказывают свежесть съёмки.
- Мультимодальное сравнение «до/после» и оценка качества ремонта без модели не заявляются.
- Telegram-адаптер выключен, пока не заданы `NARYADAI_TELEGRAM_ENABLED=1`, `NARYADAI_TELEGRAM_BOT_TOKEN` и `NARYADAI_TELEGRAM_WEBHOOK_SECRET`. `/api/telegram/pair` выдаёт одноразовый 12-символьный код на 10 минут; привязка принимается только командой `/start <код>` в личном чате при совпадении отправителя и chat ID. После привязки доступны `/start`, `/help`, `/status`, `/menu`, `/orders [страница]`, «Мои наряды», «Предыдущая страница» и «Следующая страница». Исполнитель видит назначенные ему наряды, мастер — назначенные ему как ответственному, руководитель — все наряды только для просмотра. Кнопки не меняют состояние наряда; каждое сообщение заново проверяет роль, чат и состав доступных назначений. Входной лимит — 120 приватных обновлений в минуту на общую базу SQLite, не более 100 ожидающих bot-command/pair-help записей и 20 000 дедупликационных update ID; при заполнении inbox новые обновления отбрасываются до административного обслуживания. Ввод ограничен 256 символами, пользовательский текст экранируется. `NARYADAI_PUBLIC_SITE_URL` принимает только постоянный HTTPS origin; временные туннели и URL с путём отклоняются. Просроченные уведомления остаются короткими allowlist-шаблонами только для назначенного исполнителя и мастера. Очередь и fake sender проверены; бот, ключи, внешний webhook и реальные сообщения не создавались/не отправлялись. Streamlit embedded backend намеренно удаляет настройки интеграций.
- For the approved demo only, set NARYADAI_PUBLIC_SITE_URL to https://legless-bennie-sheepish.ngrok-free.dev and NARYADAI_ALLOW_DEMO_TUNNEL=1; all other tunnel hosts remain blocked.
- Streamlit-вариант намеренно удаляет все переменные LLM/Telegram из embedded backend, поэтому внешние сервисы там не вызываются даже при наличии таких переменных в процессе. Интеграции доступны только отдельно настроенному API/PWA серверу.
- Webhook требует публичный HTTPS URL; сервер на `127.0.0.1` недоступен Telegram. Перед интеграцией нужен одобренный хост, владелец бота и секретное хранилище для перечисленных переменных. В текущем демо внешние сообщения не отправлялись.
- Service worker кэширует только оболочку приложения. Офлайн-запись и синхронизация команд не реализованы. Для установки Android PWA нужен `localhost` или HTTPS; простой HTTP-доступ к ПК из локальной сети не даёт надёжного installable PWA.

## Ограничения и безопасность

Это локальный демонстрационный прототип, не производственная система. HTTP-сервер привязан к `127.0.0.1` по умолчанию; в нём нет TLS, интеграции с корпоративной учётной записью, управления администратором, регламента смен предприятия и утверждённых нормативов расхода/трудоёмкости. Значения каталога — только учебные примеры; источник и версия показаны, неизвестные комбинации остаются `unknown`, сравнение не влияет на рейтинг. Не открывайте его в сеть предприятия и не загружайте непубличные производственные материалы.

НарядКонтроль регистрирует ремонтную работу и не является нарядом-допуском. Он не выдаёт разрешение на опасную работу, не подтверждает безопасность, не заменяет инструктаж, внешние документы, подписи или решение ответственного лица. Описанный пользователем личный опыт подписания документов не подтверждён как регламент заказчика. Отказ или пауза из-за отсутствия допуска не штрафуется автоматически: необоснованность отказа может отметить только мастер с аудируемой причиной.

Сессии хранят хеш opaque-токена, пароль сверяется PBKDF2-HMAC-SHA256, изменяющие запросы требуют CSRF-токен, роль и область наряда проверяются на сервере. У менеджера только GET-доступ. Подробная [матрица требований](docs/requirements-and-scope.md) и [API для будущего Flutter-клиента](docs/api.md) описывают границы и права сервера.

## Docker

`docker compose up --build` собирает API/PWA и хранит SQLite/фото в именованном volume `naryadai-data`; локальный порт привязан только к `127.0.0.1:8765`. В этой сессии Docker CLI найден (29.6.2), но Compose-плагина нет, а подключение к Docker daemon недоступно; сборка и запуск образа не проверены. `docker compose down` сохраняет данные; `docker compose down -v` удаляет volume с базой и фото. Переменные пусты, поэтому LLM остаётся в `rules-only`. Внешний HTTPS, push, публичный host и постоянный удалённый диск этим файлом не создаются.

Опциональный UI поверх API: `docker compose --profile demo-ui up --build` (Streamlit на `127.0.0.1:8501`). В Compose задан `NARYADAI_API_URL=http://app:8765`, поэтому роли и данные проверяет отдельный `server.py`, а SQLite и фото лежат в volume API. Если запустить `streamlit_app.py` без `NARYADAI_API_URL`, он сам поднимет один loopback API с временным SQLite и синтетическими образцами.

AppTest проверяет UI через встроенный API без отдельного процесса `server.py`: `python tests/run_streamlit_apptest.py`. Проверки включают выбор участка и оборудования, изоляцию сессий и прав, очередь, паузу, синтетический образец, проверку ИИ, доработку и закрытие. `python tests/run_streamlit_cloud_smoke.py` запускает только команду Streamlit и проверяет HTTP-запуск.

### Render Free — только эфемерное демо

После отдельного разрешения на подключение откройте Render Dashboard → New → Web Service и на живом экране GitHub разрешите доступ только к выбранному репозиторию. Выберите runtime Docker, Dockerfile `Dockerfile` и health check path `/api/health`; сервер использует переменную `PORT` Render (по умолчанию 10000). Секреты интеграций оставьте незаданными. Render собирает `Dockerfile`, а не `compose.yaml`: локальные Compose-настройки тома, `read_only` и `tmpfs` там не применяются.

Бесплатный сервис засыпает после периода бездействия и пробуждается с задержкой. Его файловая система эфемерная: SQLite и загруженные фото могут сбрасываться при засыпании, перезапуске или повторном развёртывании; бесплатный план не поддерживает persistent disk. Используйте этот режим только как демо на синтетических данных. Для локального Docker named volume `naryadai-data` сохраняет базу и фото между обычными остановками Compose; `docker compose down -v` удаляет его. См. [Render Web Services](https://render.com/docs/web-services), [Docker on Render](https://render.com/docs/docker) и [ограничения Free](https://render.com/docs/free).

## Streamlit Community Cloud — только демо

Укажите `streamlit_app.py` как entrypoint, выберите Python 3.12 в настройках приложения и оставьте `NARYADAI_API_URL` незаданным. Корневой `requirements.txt` закрепляет локально проверенные версии Streamlit, Requests и Pillow. Приложение один раз запускает канонический `server.py` внутри процесса Streamlit, только на `127.0.0.1` и порту, выбранном ОС; API-порт наружу не публикуется.

Это не production-хостинг. SQLite и фото хранятся во временном каталоге: сон или перезапуск может сбросить их. Демо-аккаунты, наряды и загрузки общие для участников, поэтому используйте только встроенные синтетические изображения и не вводите реальные персональные, производственные или данные безопасности. В этом режиме отключены внешний LLM и доставка Telegram. Картинки служат только для проверки загрузки и не доказывают состояние оборудования. Обновление задано через Streamlit fragment с интервалом 5 секунд; AppTest проверяет обновление после действий, но периодический интервал в реальном браузере и Cloud здесь не измерялся. Развёртывание в Streamlit Community Cloud не выполнялось и там не проверялось.


## Evidence semantics for materials and equipment downtime

- A completed legacy order with no `order_materials` rows and `materials_not_used=0` has **unknown** actual consumption. Its actual quantity and difference stay unknown. Only an explicit `materials_not_used=true` with an empty materials list confirms zero use.
- Completion rejects `materials_not_used=true` together with material rows before changing the order, material rows, audit, or notifications.
- If an older database already contains both the flag and material rows, the stored quantities remain visible with `materials_evidence_status=conflict`; the reference difference is not calculated and no rating is derived from it.
- Equipment downtime intervals are unioned per asset in seconds; the final totals convert to minutes at three decimal places. Sub-minute intervals remain visible across adjacent shifts.
- Equipment type migration backfills only the 25 exact code/name pairs from the deterministic seed. Every nonmatching legacy asset stays `unknown`.


## Manual work queue

The responsible master can set a per-worker or per-brigade active-work sequence with up/down controls in the PWA or Streamlit panel. The worker sees the persisted position; the manager remains read-only. Queue order does not change priority, due date, status, or assignment. The API checks a versioned complete queue inside a SQLite write transaction, rejects stale or cross-scope writes, and audits position changes. Assignment/status changes invalidate in-flight revisions. Legacy and new unpositioned orders retain a deterministic priority/deadline fallback. See [API details](docs/api.md), [requirements](docs/requirements-and-scope.md), and [demo script](docs/demo-script.md).
