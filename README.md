# EnbekPlus · ЕңбекПлюс

Демонстрационная система ремонтных нарядов для кейса №1 Qostanai AI Industry Hackathon 2026: мастер выдаёт задание, исполнитель фиксирует ход и результат работы, мастер принимает результат, руководитель читает отчётность. В репозитории находятся Python API, браузерная PWA, дополнительный Streamlit-интерфейс и Flutter-клиент Android.

Это MVP на синтетических данных. Система не выдаёт наряд-допуск, не подтверждает исправность оборудования и не разрешает опасные работы.

## Возможности и роли

### Мастер

- Создание планового или внепланового наряда: участок, оборудование, описание, приоритет, исполнитель либо бригада и срок
- Фото «до» необязательны; до пяти активных файлов можно добавить при выдаче или позднее в допустимом статусе
- Доска работ, фильтры, нагрузка, просрочки, история оборудования, переназначение до принятия/после отказа, отмена и повторная выдача с аудитом
- Ручная последовательность активной очереди исполнителя/бригады в PWA и Streamlit; версия очереди защищает от устаревших перестановок
- Проверка результата, направление на доработку, отдельный комментарий при закрытии и оценка с объяснением
- Регистрация закрытого интервала простоя оборудования с причиной; отчёты за период

### Исполнитель

- Собственные назначения и доступные новые задания своей бригады
- Принятие, очередь, отказ с причиной, начало, пауза/возобновление, выполнение и повторная сдача
- Текст выполненной работы, код неисправности, фактические часы, материалы с количеством либо явное подтверждение, что материалы не использовались
- Фото «после», необязательный отдельный комментарий и просмотр результата проверки/окончательной оценки

### Руководитель

- Общий просмотр нарядов, отчётов, рейтинга и аудита
- Изменение нарядов и приёмка недоступны; необязательная привязка собственного Telegram-чата не даёт прав менять работы

Права проверяются сервером на каждом маршруте. Скрытая кнопка в интерфейсе не является механизмом авторизации. Функции клиентов отличаются: полная доска, отчётность и управление очередями доступны в PWA/Streamlit; Flutter реализует мобильный ролевой цикл наряда, фото, настройки, Telegram-привязку и просмотр сохранённого анализа. Полное совпадение всех экранов клиентов не заявляется.

### Жизненный цикл

Основной путь: `issued → accepted → in_progress → executed → ai_review → closed`.

Дополнительные состояния: `queued`, `paused`, `rejected`, `rework`. Допустимые переходы зависят от роли и текущего состояния; возврат на доработку сохраняет историю. Отмена использует отдельный флаг и статус `rejected`. Просрочка является отдельным признаком, а не одиннадцатым статусом.

Срок наряда и фактические трудозатраты учитываются раздельно. Совместимое API-поле `norm_hours` при выдаче задаёт контрольный срок, а не утверждённую норму труда. Окончательное закрытие выполняет мастер с отдельным комментарием.

## Архитектура и состав репозитория

```text
server.py                   HTTP API, SQLite, роли, переходы, таймер, интеграции
static/                     PWA: HTML, CSS, JavaScript, manifest, service worker
streamlit_app.py            дополнительный Python UI
requirements-api.txt        зависимости API
requirements-streamlit.txt  зависимости Streamlit и AppTest
requirements.txt            зависимости варианта Streamlit Community Cloud
Dockerfile                  API/PWA образ на Python 3.12
Dockerfile.streamlit        дополнительный Streamlit-образ
compose.yaml                локальный API + опциональный Streamlit-профиль
.env.example                шаблон без секретов, интеграции выключены
tests/                      Python, Node, AppTest и HTTP-контрактные проверки
docs/                       API, сценарий, границы, отчёты о прошлых проверках
demo_photos/                синтетические изображения для демонстрации
mobile_flutter/             Flutter v3 + analyzer hotfix и Android scaffold
```

Backend является источником состояния: SQLite хранит наряды, учётные записи, аудит, очереди и метаданные фото; файлы изображений лежат в каталоге данных. По умолчанию каталог — `data/`, его можно изменить через `NARYADAI_DATA_DIR`. База и рабочие фото не являются исходным кодом и не должны попадать в Git.

PWA и Streamlit используют HTTP API. Flutter использует тот же сервер: opaque session cookie и CSRF-токен держатся в памяти клиента; JSON-запросы передаются с корректным `Content-Length`. Защищённые фото читаются через `/api/photos/{id}` с проверкой доступа, а не через произвольный URL из ответа. Настройки языка/темы сохраняются отдельно от сессии.

Pillow декодирует изображения, извлекает EXIF и вычисляет признаки похожести. Внешняя LLM и Telegram являются отдельными опциональными адаптерами, выключенными по умолчанию.

## Локальный запуск Python 3.12

Команды ниже — инструкция для собственной среды, а не сообщение о новом выполненном прогоне. Выполняйте их из корня репозитория. Нужны Python 3.12 и доступ к установке зависимостей.

### Linux / macOS

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-api.txt
python server.py
```

### Windows PowerShell

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-api.txt
.\.venv\Scripts\python.exe server.py
```

При подготовленном Python 3.12 можно использовать `start-enbekplus.ps1`; основной переносимый вариант выше не требует изменения политики выполнения PowerShell.

Откройте `http://127.0.0.1:8765`. Проверка доступности: `http://127.0.0.1:8765/api/health`. Ответ — `{"ok":true,"app":"EnbekPlus","mode":"local-mvp"}`. Остановка — `Ctrl+C`.

Для другого локального порта: `python server.py --port 8768`. Сервер по умолчанию слушает только `127.0.0.1`. Параметры `--host`, `--port`, `--db` и переменные `NARYADAI_HOST`, `NARYADAI_PORT`, `NARYADAI_DATA_DIR` задают конфигурацию; не открывайте демонстрационный HTTP-сервер в сеть предприятия.

## Локальный Docker

Нужны установленный Docker с Compose и доступ к базовому образу/зависимостям. Проверка файла конфигурации не равна проверке запущенного контейнера; Docker build и Compose runtime для серверного архива не были выполнены.

```sh
docker compose up -d --build app
docker compose ps
docker compose logs --tail=100 app
```

API/PWA: `http://127.0.0.1:8765`. Compose публикует порт только на loopback хоста. Именованный том `naryadai-data` сохраняет SQLite и фото между обычными остановками. Контейнер запускается непривилегированным пользователем, с read-only root filesystem и отдельным временным каталогом; это не заменяет production-проверку безопасности.

Дополнительный Streamlit UI:

```sh
docker compose --profile demo-ui up -d --build
```

Адрес: `http://127.0.0.1:8501`; в этом профиле Streamlit подключается к отдельному сервису `app`.

Для остановки используйте `docker compose stop` или обычный `docker compose down`. **Не выполняйте `docker compose down -v` для обновления:** эта команда удаляет том с данными.

### Обновление уже работающего экземпляра

1. Сохраните согласованную резервную копию SQLite и файлов фото штатным способом
2. Перенесите исходники в существующий Compose-проект, сохранив локальный `.env` и данные
3. Проверьте имя Compose-проекта и тома: запуск из нового каталога может создать новый пустой том
4. Пересоберите и пересоздайте `app` штатной командой проекта; не удаляйте data volume
5. Проверьте `/api/health`, вход, наряд и фото; обновите PWA онлайн для установки новой оболочки service worker

Эти действия выполняются отдельно на хосте. Обновление GitHub само по себе не запускает их.

### Streamlit без Docker

```sh
python -m pip install -r requirements-streamlit.txt
python -m streamlit run streamlit_app.py
```

Если `NARYADAI_API_URL` не задан, Streamlit запускает embedded backend только на loopback со случайным портом. В embedded-режиме настройки LLM/Telegram намеренно удаляются, внешние интеграции недоступны. При подключении к отдельному API его конфигурацией управляют отдельно.

Streamlit Community Cloud описан как демонстрационный вариант, но его deployment здесь не выполнен и не проверен. Временное хранение, общие демо-аккаунты и возможный сброс данных не подходят для производственной эксплуатации.

## Flutter / Android

Подробности, ограничения и команды: [mobile_flutter/README.md](mobile_flutter/README.md).

Мобильный интерфейс включает RU/KK/EN, светлую/тёмную/системную тему, ролевой цикл наряда, создание мастером, фото из камеры/галереи, просмотр защищённых фото, Telegram-настройки и сохранённый анализ. Произвольные тексты нарядов, ответа модели и комментариев остаются на исходном языке; внешний переводчик не вызывается.

v3 добавляет отдельные поля режима, вывода, замечаний, проверки фото/материалов, `report_score`, `score_reason`, `confidence` и окончательной оценки мастера. Старый результат после доработки маркируется как предыдущий. Режим модели показывается лишь при согласованных серверных полях; экран не подтверждает живой вызов модели. Оценка проверяемости фото и оценка текста отчёта не равны оценке качества ремонта.

### Предварительные условия сборки

- Совместимые Android SDK/JDK и подготовленный Android-проект
- Доступный в собственной доверенной среде полный Gradle wrapper: `gradle-wrapper.jar` в репозитории отсутствует; этот пакет его не создаёт, не скачивает и не передаёт
- Успешное разрешение зависимостей и проверенный актуальный `pubspec.lock`; сохранённый старый lock не является доказательством воспроизводимости v3

Release-подпись, магазин приложений и iOS-сборка не входят в поставку.

### Подключение к серверу

В поле адреса на экране входа укажите доступный устройству API origin и фактический порт:

- Android-эмулятор на том же хосте, сервер по умолчанию: `http://10.0.2.2:8765`
- В исходном поле клиента пока указан пример `http://10.0.2.2:8768`; оставляйте его только если API действительно слушает 8768
- `127.0.0.1` на телефоне означает сам телефон. Физическое устройство не получает доступ к loopback-порту компьютера автоматически
- Для подключения телефона нужен отдельно согласованный доступный адрес, предпочтительно HTTPS, и соответствующая сетевая конфигурация. Не публикуйте демо-сервер наружу лишь ради обхода ошибки соединения

PWA и нативный Flutter-клиент — разные способы доступа. Service worker кэширует оболочку PWA; офлайн-запись и последующая синхронизация команд не реализованы. Возможность установки PWA на устройстве требует отдельной проверки и безопасного контекста.

## ИИ: безопасный opt-in и честные режимы

По умолчанию `NARYADAI_LLM_ENABLED=0`, `NARYADAI_LLM_REPORT_SUMMARY=0`; ключ и модель пустые. Наличие ключа само по себе не включает обращения. Без включённой полной конфигурации или при ошибке адаптера результат явно обозначается `rules-only`.

`rules-only` — локальные проверки заполненности и правил. Он не является смысловой LLM-проверкой. Адаптер реальной модели предусмотрен, но его внешняя работа, качество и стоимость в этой поставке не проверялись.

Для отдельно разрешённого теста только на синтетических данных:

1. Создайте локальный `.env` по [.env.example](.env.example); секреты введите только локально/через менеджер секретов
2. Задайте `NARYADAI_LLM_ENABLED=1`, `NARYADAI_LLM_API_KEY` и `NARYADAI_LLM_MODEL`
3. При необходимости задайте `NARYADAI_LLM_API_URL`: только HTTPS; пустое значение использует предусмотренный Gemini OpenAI-compatible endpoint
4. Перезапустите/пересоздайте свой API-сервис с этой конфигурацией, сохраняя данные
5. Проверьте режим и результат конкретного запроса. Установленный флаг или надпись в старом результате не доказывают успешный живой вызов

Адаптер отправляет текст отчёта (до 8000 символов) и ограниченный контекст: проблему, оборудование, код, тип работ, до 20 строк материалов, отметку об отсутствии расхода, фактические часы, время относительно срока и число уникальных фото после работы. Обрезание/недостаток существенных данных блокирует автоматический положительный результат и требует решения мастера. Это внешняя передача данных выбранному провайдеру. Детектор очевидных контактов/секретов не гарантирует анонимизацию любого текста.

Для сводки отчёта отдельно нужны `NARYADAI_LLM_REPORT_SUMMARY=1`, включённая LLM, явный запрос мастера/руководителя и минимум пять нарядов. Передаются период и агрегаты; обычное обновление отчёта не запрашивает модель.

Для отключения новых обращений верните оба флага в `0` и пересоздайте API-сервис. Не публикуйте `.env`, ключи, токены или раскрытый вывод `docker compose config`. Не используйте реальные персональные и производственные сведения без отдельного разрешения и оценки защиты данных.

## Telegram: отдельная необязательная интеграция

По умолчанию `NARYADAI_TELEGRAM_ENABLED=0`, `NARYADAI_TELEGRAM_BOT_TOKEN` и `NARYADAI_TELEGRAM_WEBHOOK_SECRET` пустые. Для включения существующего адаптера нужны флаг `1` и оба секрета; без secret webhook не принимается. Создание бота, публичного HTTPS endpoint и регистрация webhook выполняются отдельно.

- Привязка: одноразовый `/start CODE`, 10 минут, только личный чат с совпадающим отправителем/chat ID
- Команды `/start`, `/help`, `/status`, `/menu`, `/orders` и постраничные кнопки дают чтение в рамках роли
- Из Telegram нельзя изменять статус наряда
- Перед доставкой сервер повторно проверяет роль, назначение и чат; есть ограничения входа, дедупликация и outbox
- Неопределённый исход сетевой отправки не означает подтверждённую доставку; гарантии exactly-once нет

Для разрешённого теста используйте отдельного тестового бота и синтетические данные. В `.env.example` есть настройки публичного адреса, но текущий `compose.yaml` не передаёт `NARYADAI_PUBLIC_SITE_URL` и `NARYADAI_ALLOW_DEMO_TUNNEL` в контейнер: наличие этих строк в `.env` само по себе их не применяет. Публичный адрес и его передачу процессу нужно проверить отдельно; временные туннели не являются production-решением, исключение для демонстрационного туннеля по умолчанию выключено.

Проверялись fake webhook/sender и локальная очередь. Реальный бот, внешняя регистрация webhook и доставка Telegram не проверялись. Для прекращения новых доставок верните `NARYADAI_TELEGRAM_ENABLED=0` и пересоздайте сервис.

## Фото, материалы и границы доказательств

- Принимаются JPEG/PNG/WebP до 4 МБ, до пяти активных фото каждой фазы. Проверяются декодирование, точные и похожие дубли
- Похожесть по dHash — сигнал возможного повторного использования; кадрирование, поворот и другие изменения могут обойти сравнение
- EXIF может отсутствовать или быть изменён. Без часового пояса он не придумывается. Оценка фото описывает проверяемость файла, а не качество ремонта
- Фото, EXIF и время загрузки не доказывают свежесть съёмки, устранение неисправности или безопасность оборудования
- При возврате на доработку прежние фото «после» деактивируются с сохранением аудита; для повторной сдачи нужны новые допустимые фото. Ожидающая очистка файлов может временно блокировать загрузку
- Мультимодальная проверка «до/после» и автоматическое подтверждение качества ремонта не заявляются
- Отсутствие строк материалов не означает нулевой расход. Ноль подтверждается явным `materials_not_used=true`; конфликт со строками материалов не превращается в расчёт или штраф
- Справочные часы/материалы синтетические. Неизвестное соответствие остаётся `unknown`, сравнение не меняет рейтинг
- Паузы исполнителя, фактические часы и вручную зарегистрированный простой оборудования — разные показатели. Простой не выводится автоматически из фото или статуса; пересекающиеся интервалы объединяются по оборудованию в UTC

### Повторение серверных проверок

На отдельной синтетической среде Python 3.12 установите `requirements.txt`, подготовьте Node.js, выключите LLM/Telegram и не используйте рабочие секреты:

```sh
python -m pip install -r requirements.txt
python -m unittest discover -v
node --check static/app.js
node --check static/sw.js
node --test tests/test_frontend_races.js
python tests/run_streamlit_apptest.py
python tests/run_flutter_v2_contract.py
```

Последняя команда выполняет Python HTTP-запросы, соответствующие контракту клиента, а не запускает Flutter. Опциональный `tests/run_pwa_reporting_smoke.py` требует отдельной браузерной среды; прежний Chromium smoke был заблокирован ограничением socket и не считается пройденным.

## Демонстрация и пакет подачи

1. Запустите локальную синтетическую среду, оставив внешние интеграции выключенными
2. Мастером создайте внеплановый наряд для `worker01`; фото «до» можно пропустить
3. Исполнителем примите задание, начните работу и заполните отчёт, часы, код и расход материалов
4. Покажите честный `rules-only`: без фото «после» внеплановая работа требует доработки
5. Добавьте допустимое синтетическое фото после начала доработки, повторно сдайте, затем мастером проверьте и закройте с комментарием
6. Покажите анализ отдельно от окончательной оценки, аудит и read-only доступ руководителя

Полный сценарий: [docs/demo-script.md](docs/demo-script.md). Для показа используйте только вымышленные данные и синтетические фотографии.

Для честной передачи жюри/проверяющему подготовьте:

- Ссылку на конкретный commit и доступ к приватному репозиторию для названных проверяющих; приватная ссылка сама по себе доступ не предоставляет
- README, инструкцию запуска и перечень ограничений
- Архив исходников без секретов, баз, рабочих фото, кэшей, окружений и бинарных артефактов, не входящих в согласованную поставку
- Если передаётся APK отдельно: сам файл, SHA-256, тип debug/release, версии SDK, commit, актуальный lockfile и реально выполненные проверки
- Короткую запись/скриншоты демонстрации с точным указанием, какой сервер и какой клиент использовались
- Явный список непроверенного: живой ИИ, Telegram, deployment и проверки устройства, если они ещё не выполнены

Ссылки на APK и заявления «100% готово» не подменяют отсутствующие артефакты/проверки. Лицензионные права на внешние SDK и зависимости определяются их собственными условиями.

## Ограничения безопасности

Демонстрационный сервер не содержит промышленной системы учётных записей, SSO, полного администрирования, TLS-терминации, утверждённых нормативов/графиков предприятия и подтверждённых допусков работников. Встроенные демо-пароли известны. Для реального развёртывания необходимы отдельные проектирование защиты, доступов, хранения, резервного копирования, эксплуатации и проверка интеграций.

Рейтинг и учебные ориентиры не предназначены для автоматических кадровых решений. Ни LLM, ни фото, ни ручная регистрация времени не заменяют ответственного специалиста и требования промышленной безопасности.
